## 🧭 FAZA 0 — Kontekst (co przeczytałem z kodu)

Przeczytałem rdzeń pipeline'u oraz zweryfikowałem empiryczne fakty z brief'u bezpośrednio w kodzie. Poniżej destylat — to fundament, na którym stoi cała ideacja.

### 0.1. `start.py` — dyrygent pipeline'u

`main()` (linie 381–396) to **liniowa sekwencja pytań Y/N**, każdy krok bramkowany przez `ask_user()`:

```
display_logo()
settings = update_settings()          # 💾 "Czy chcesz zmienić ustawienia?"
extract_tracks_from_mkv()             # 🧲 "Czy chcesz wyciągnąć ścieżki?" → potem RĘCZNY wybór ID per plik
refactor_subtitles()                  # split_ass → RĘCZNY wybór stylów per plik
translate_subtitles(settings)         # 💭 "Czy tłumaczyć?" → potem per-plik Y/N
convert_numbers_to_words()            # 🔢 per-plik Y/N
generate_audio_for_subtitles(...)     # 🎤 "Czy generować audio?" → potem per-plik Y/N
refactor_alt_subtitles()              # srt_to_ass (BUG)
process_output_files(settings)        # scalanie/wypalanie
clear_temp_folders()
```

**Anatomia bólu (skąd ~300 kliknięć przy 40 odcinkach):**

| Etap | Interakcje / odcinek | Przy 40 odc. |
|---|---|---|
| Pytanie globalne "czy wyciągać ścieżki" | (1 raz) | 1 |
| `mkv_extract_track` — wpisanie ID ścieżek + ENTER | ~2-3 | ~100 |
| `split_ass` — wybór stylów + ENTER per plik napisów | ~2-4 | ~120 |
| `translate_subtitles` — per-plik Y/N | ~1-2 | ~60 |
| `convert_numbers` — per-plik Y/N | ~1 | ~40 |
| `generate_audio` — per-plik Y/N | ~1 | ~40 |
| **Razem** | **~7-8** | **~300+** ✔️ (potwierdza szacunek usera) |

To NIE jest problem CPU — to problem **interaktywnego bramkowania**. Pipeline obliczeniowo już działa; brakuje warstwy decyzyjnej, która podejmie te decyzje za usera.

### 0.2. `modules/mkvtoolnix.py` — ekstrakcja ścieżek

- `get_mkv_info()` → woła `mkvmerge --identify --identification-format json` (linia 111–119). **To jest dokładnie to źródło metadanych, o którym mówi brief.**
- `_parse_track_data()` (linia 139–160) JUŻ wyciąga `properties.get('language')` i `properties.get('language_ietf')`. **ALE NIE czyta `track_name`** — a to kluczowe pole do rozróżniania ścieżek (`'CR'`, `'Brazilian_CR'`, `'Signs/Songs'`). To pierwsza luka do załatania.
- `_get_track_properties()` (linia 162–177) zwraca tylko wymiary/sampling — gubi `number_of_lines`, `forced`, `default`, `enabled`. Te pola są dostępne w JSON mkvmerge i będą potrzebne do scoringu ścieżek.
- `mkv_extract_track()` (linia 204–256) — **w pełni ręczny**: pętla `while True` z `input()` na ID ścieżek. To serce ~100 kliknięć. Architektura podpowiada rozwiązanie: rozdzielić **selekcję** (które ID) od **ekstrakcji** (samo `mkvextract`). Dziś są splecione.

**Wniosek:** auto-wybór ścieżek to nie nowy moduł — to **funkcja selekcji** wstawiona przed istniejącą pętlą ekstrakcji + dwa dodatkowe pola w parserze. Tani refaktor.

### 0.3. `modules/subtitle.py` — rdzeń problemu detekcji stylów

- `split_ass()` (linia 81–99) → `_select_styles()` (138–153) to **ręczna pętla `input()`**. Wyświetla style, user wpisuje numery. To serce ~120 kliknięć.
- **Co jest dobre:** kod już rozdziela napisy na `main_subs` (dialog → TTS) i `alt_subs` (znaki/efekty → zostają jako ASS). Mechanika podziału (`_split_subs`, `_copy_metadata_and_styles`, `_save_subs`) jest sprawna i format-aware (pysubs2 / `SSAFile`). **Wystarczy podmienić ŹRÓDŁO decyzji** z `input()` na funkcję scoringu. Reszta rurociągu się nie zmienia.
- `_get_styles()` (117–125) daje listę nazw stylów. Do scoringu trzeba dołożyć metryki per styl (pos%, draw%, punct%, avg_len, line_count) — czyli przejść raz po `subs` i policzyć. pysubs2 daje `event.text`, `event.style`, `event.type`.
- **BUG `srt_to_ass()` (linia 377–429)** — potwierdzony empirycznie. Newralgiczne linie:
  - 399: `if event.type == "Dialogue" and srt_index < len(srt_subs) and not re.search(r'\b(m|n) -?\d+', event.text)` — heurystyka "pomiń rysunki wektorowe" (`m 10 20...` = drawing commands). Krucha: łapie przypadkowe `m`/`n` w treści.
  - 401: `if re.search(r'{\\.*?}', event.text)` → `srt_index += 1; continue` — pomija KAŻDĄ linię z jakimkolwiek tagiem `{...}`, ale **inkrementuje `srt_index`**. To desynchronizuje mapowanie: jeśli linia ASS ma tag, traci się przypisanie tłumaczenia i przesuwa wszystko dalej. To główne źródło "każdy ASS ma inną strukturę → zawodzi".
  - 405–410: doklejanie tekstu po ostatnim `}` — działa tylko gdy struktura tagów jest prosta.

  **Diagnoza:** problem to brak **stabilnego klucza dopasowania** między SRT (przetłumaczonym) a ASS (oryginalnym). Mapowanie po kolejności (`srt_index`) pęka przy pominięciach. Rozwiązanie musi mapować po **czasie startu** (`event.start`), nie po indeksie.

### 0.4. `modules/translator.py` — translacja (kontekst, nie cel ideacji)

- 6 backendów: Google (async, automatyczny), DeepL API/Desktop, ChatGPT (ręczny — kopiuj/wklej, `getch()`), Gemini Pro (otwiera folder + `getch()` — w pełni manualny, zewnętrzne repo `github.com/MattyMroz/Gemini`).
- **Kluczowy fakt dla trybu auto:** tylko Google/DeepL API są bezobsługowe. ChatGPT/Gemini wymagają człowieka. **Tryb auto MUSI domyślnie wymuszać auto-backend** (Google/DeepL API), inaczej "auto" się zatrzyma na `getch()`. To twarde ograniczenie do uwzględnienia w FAZIE 4.
- W kodzie żyje gigantyczny prompt polonisty (linie 332–467) — dowód, że jakość tłumaczenia to dla usera priorytet. Tryb auto nie może go degradować; powinien go zachować dla backendów, które go używają.

### 0.5. `modules/mkv_processing.py` — wyjście (potwierdza preferencję PL)

- `mkv_merge()` (linia 124–139) **hardkoduje polskie wyjście**: `--language 0:pol --track-name '0:Lektor PL'` dla audio, `'0:Napisy Poboczne PL'` dla napisów. **To empiryczny dowód**, że cały produkt jest jednokierunkowy: *cokolwiek na wejściu → polski lektor + polskie napisy poboczne na wyjściu*. Auto-detekcja musi tylko ustalić **co jest źródłem dialogu** i **co jest źródłem znaków** — kierunek (→PL) jest stały. To zawęża problem.

### 0.6. `data/settings.py` + `settings.json` — gdzie wpiąć flagę trybu

- `Settings` to `@dataclass(slots=True)` (linia 38–85). `slots=True` oznacza: **nowe pole trzeba dodać jawnie w klasie** (nie da się przypisać atrybutu spoza slots). Dodanie `auto_mode` i pól pokrewnych = edycja dataclass + `load_from_file()` (mapowanie `data.get(...)`) + `change_settings_save_to_file()`.
- `load_from_file()` (115–178) ma wzorzec `data.get('klucz')` z domyślnymi — łatwo dołożyć `auto_mode: bool = False` z bezpiecznym defaultem (wsteczna kompatybilność: stary `settings.json` bez pola → tryb ręczny). ✔️ zgodne z Tablicą Prawdy #4.
- `settings.json` (aktualny) pokazuje realne wartości: `tts: "TTS - ElevenBytes"`, `translator: "Google Translate"` (uwaga: w kodzie `translate_srt` mapuje po stringu — patrz 0.4). To znaczy: **user już dziś używa auto-backendu Google** → tryb auto jest realny bez zmiany nawyków.

### 0.7. Zasoby zewnętrzne (sibling projects) — zweryfikowane

- `EchoReader/` istnieje i zawiera własną infrastrukturę LLM (potwierdzone: katalog `knowledge/`, `.prompts/`, referencje do modeli lokalnych). User deklaruje, że MA pobieracz + moduł GGUF (Gemma) w innym projekcie — traktuję to jako **dostępny, ale opcjonalny** klocek.
- `TTS/` zawiera `elevenbytes`, `fish-speech`, `slop-tts`, `omnivoice` — bogactwo backendów audio (spójne z 8 silnikami w `Config.get_voice_actors()`).
- Repo `github.com/MattyMroz/Gemini` (z `translate_gemini`) — zewnętrzny, manualny tłumacz.

**Konkluzja FAZY 0:** Pipeline jest *gotowy obliczeniowo*. Brakuje **warstwy decyzyjnej**, która zastąpi 7-8 ręcznych decyzji per odcinek. Trzy decyzje są trywialne dzięki metadanym (które ścieżki audio/napisów), jedna jest trudna (podział stylów dialog vs znaki), jeden bug blokuje czysty obieg napisów pobocznych (`srt_to_ass`). To definiuje zakres.

## 🛡️ FAZA 1 — Definicja problemu + Tablica Prawdy

### 1.1. Problem w jednym zdaniu

> **Zamienić ~7-8 ręcznych decyzji na odcinek (~300 kliknięć / 40 odcinków) w deterministyczny, offline'owy proces wsadowy, który dla folderu pełnego MKV sam wybierze właściwe ścieżki, rozdzieli dialog od znaków, przetłumaczy i wygeneruje lektora — pytając człowieka TYLKO przy realnej niepewności.**

### 1.2. Dekompozycja na 4 pod-problemy

| # | Pod-problem | Trudność | Źródło prawdy | Czy potrzebny LLM? |
|---|---|---|---|---|
| **A** | Wybór ścieżki **audio** (zwykle JP, czasem inne) | 🟢 Niska | metadane `language` + `track_name` | ❌ Nie |
| **B** | Wybór **właściwej ścieżki napisów** (pełny dialog vs „tylko znaki/songs”) | 🟡 Średnia | metadane + liczba linii + rozkład czasowy | ❌ Nie (heurystyka strukturalna) |
| **C** | **Podział stylów** w ASS (dialog → TTS vs znaki/efekty → ASS) | 🔴 Wysoka | metryki treściowe ASS (pos%, draw%, punct%) | ⚠️ Opcjonalnie jako fallback |
| **D** | **Bug `srt_to_ass`** (scalanie tłumaczeń pobocznych do ASS) | 🟡 Średnia | czas startu eventów (mapowanie) | ❌ Nie (to bug inżynieryjny) |

To kluczowa obserwacja całej ideacji: **tylko jeden pod-problem (C) ma realną niepewność, która MOGŁABY uzasadniać LLM.** A i B to czytanie metadanych. D to bug do naprawienia. Pytanie "LLM czy nie?" sprowadza się więc do: *"czy heurystyka metryczna na pod-problemie C jest wystarczająco dobra, by LLM był zbędny w 95%+ przypadków?"* — i brief mówi: ~90% sama metryka, ~90% sama nazwa, ale z różnymi dziurami. To sugeruje **hybrydę** (nazwa+metryka) > każde z osobna.

### 1.3. 🔒 TABLICA PRAWDY (święte zasady — żelazne ograniczenia)

Każdy pomysł w FAZIE 2 dostaje ocenę zgodności z każdą zasadą: ✅ spełnia / ⚠️ częściowo / ❌ łamie.

| # | Zasada (cytat intencji usera) | Konsekwencja projektowa |
|---|---|---|
| **TP-1** | 🔒 **NIE uzależniać od LLM.** „Będzie wolniejsze, trenowanie własnego to ból, dużo da się heurystykami i badaniem złożoności ASS”. LLM = OSTATECZNOŚĆ (tylko opcjonalny fallback, nigdy wymóg). | Rdzeń detekcji MUSI być deterministyczny. LLM (lokalny/API) wolno wpiąć **wyłącznie** jako wyłączalny `fallback`, który nigdy nie jest na ścieżce krytycznej. Domyślnie wyłączony. |
| **TP-2** | 🔒 **Część detekcyjna działa bez internetu.** (Translacja/TTS mogą używać sieci, ale wybór ścieżek/stylów — nie). | Detekcja A/B/C/D = czyste lokalne obliczenia (mkvmerge JSON + parsing ASS). Zero zależności sieciowej w warstwie decyzji. Wyklucza LLM API jako *wymóg*. |
| **TP-3** | 🔒 **HITL tylko przy DUŻEJ niepewności.** Może zapytać usera, ale nie za każdym odcinkiem. | Potrzebny **próg pewności** (confidence). Powyżej progu → auto. Poniżej → kolejka pytań (najlepiej zbiorcza, nie per-odcinek w trakcie). Cel: <5% odcinków pyta. |
| **TP-4** | 🔒 **Tryb ręczny pozostaje opcją.** Czasem user chce sam wybrać. | Flaga `auto_mode` w settings; default = ręczny (wsteczna kompatybilność). Ścieżka ręczna = istniejący kod `_select_styles`/`mkv_extract_track` bez zmian. Tryb auto = nakładka, nie zamiennik. |

**Test lakmusowy każdego pomysłu:** *„Czy program uruchomiony z odpiętym kablem sieciowym i bez żadnego LLM nadal podejmie decyzje A/B/C/D?”* Jeśli NIE → pomysł łamie TP-1/TP-2 i nie może być rdzeniem.

## 💡 FAZA 2 — DYWERGENCJA (15 pomysłów)

> Generuję szeroko, oceniam uczciwie. Każdy pomysł: opis · mechanizm · 💪 mocne · ⚠️ słabe · 🎲 ryzyko · ⭐ ocena (z uzasadnieniem) · 🛡️ test Tablicy Prawdy.
> Pomysły pogrupowane: **(C) detekcja stylów [P1-P7]**, **(A/B) wybór ścieżek [P8-P11]**, **(arch) architektura trybu auto [P12-P14]**, **(D) bug srt_to_ass [P15]**.

### Grupa C — Detekcja stylów (dialog vs znaki/efekty)

---

#### P1 — Czysta heurystyka metryczna (scoring treściowy bez nazw)

**Opis:** Ignoruj nazwy stylów całkowicie. Dla każdego stylu policz metryki z brief'u i sklasyfikuj progiem.

**Mechanizm:** Dla każdego unikalnego `style` w ASS przejdź po eventach i policz:
- `pos%` = % linii zawierających `\pos|\move|\clip|\fad|\t(`
- `draw%` = % linii z tagiem rysowania `\p[1-9]` (twardy sygnał: to kształty, NIGDY dialog)
- `punct%` = % linii kończących się interpunkcją zdaniową `.?!…`
- `avg_len` = średnia długość tekstu (po zdjęciu tagów)
- `line_count` / `total_lines` = udział stylu
Reguła: `draw% > 30 → ZNAK`; `pos% > 80 → ZNAK`; `punct% > 50 ∧ avg_len > 15 ∧ pos% < 20 → DIALOG`; reszta → niepewne.

**💪 Mocne:** Czysto offline, deterministyczne, szybkie (jeden przebieg). Odporne na bezsensowne nazwy (`Q1`, `Q2`). Łapie przypadek z brief'u „styl 'Sign' to faktycznie dialog” (bo patrzy na treść, nie nazwę).
**⚠️ Słabe:** Brief: sama metryka ~90%. Gubi krótki dialog bez interpunkcji (wykrzyknienia „Hai!”, „Nani?!”), karaoke z `\k` ale bez `\pos`, dialog z `\pos` (rzadkie, ale bywa — np. SMS na ekranie czytany na głos).
**🎲 Ryzyko:** Progi dobrane na jednej grupie wydawniczej mogą nie generalizować. Niskie — łatwo dostroić.
**⭐ Ocena: 8/10** — _Uzasadnienie:_ Najlepszy pojedynczy fundament: w 100% spełnia Tablicę Prawdy, deterministyczny, mierzalny. Traci 2 oczka, bo „sama metryka” ma znane dziury (brief), które domyka dopiero połączenie z nazwą (P3).
**🛡️ TP:** TP-1 ✅ · TP-2 ✅ · TP-3 ✅ (niepewne → HITL) · TP-4 ✅.

---

#### P2 — Heurystyka nazewnicza (klasyfikacja po nazwie stylu)

**Opis:** Klasyfikuj po nazwie stylu wg słownika wzorców.

**Mechanizm:** Regex/lista: `Default|Dialog|Main|Alt|Italics|Top → DIALOG`; `Sign|Song|OP|ED|Title|Caption|TS|Note|Karaoke|kfx → ZNAK`. Case-insensitive, też podciągi.

**💪 Mocne:** Trywialne, błyskawiczne, zero parsowania treści. Działa świetnie dla „grzecznych” grup (Default = dialog).
**⚠️ Słabe:** Brief explicite: nazwy bywają `Q1`,`Q2` (bezsensowne) → 0% trafień; styl `Sign` bywa dialogiem → fałszywie odrzuci dialog. Brief: sama nazwa ~90% ale z DZIURAMI tam, gdzie metryka działa.
**🎲 Ryzyko:** Cicha utrata dialogu (styl `Sign`=dialog wyląduje w alt_subs → brak lektora dla części kwestii). Wysokie i podstępne (błąd niewidoczny aż user usłyszy ciszę).
**⭐ Ocena: 5/10** — _Uzasadnienie:_ Sam w sobie zawodny i ryzykowny (ciche gubienie dialogu to najgorszy tryb porażki dla lektora). Cenny TYLKO jako sygnał wspierający w hybrydzie, nie jako decydent.
**🛡️ TP:** TP-1 ✅ · TP-2 ✅ · TP-3 ⚠️ (sam nie wie, kiedy jest niepewny) · TP-4 ✅.

---

#### P3 — ⭐ Hybryda nazwa + metryka (scoring ważony z głosowaniem)

**Opis:** Połącz P1 i P2: nazwa daje *priors* (wstępną hipotezę), metryka *weryfikuje/nadpisuje*. Gdy oba zgodne → wysoka pewność. Gdy w konflikcie → metryka wygrywa (bo treść > etykieta), ale obniż pewność → ewentualnie HITL.

**Mechanizm:** Funkcja `classify_style(style) → (label, confidence)`:
1. `name_vote` z P2 (DIALOG/ZNAK/UNKNOWN).
2. `metric_vote` z P1 (DIALOG/ZNAK/UNKNOWN) + surowe metryki.
3. Reguły fuzji:
   - `draw% > 30` → **ZNAK, conf=0.99** (twardy override, kształty to nie mowa — bije wszystko).
   - oba = DIALOG → DIALOG, conf=0.95.
   - oba = ZNAK → ZNAK, conf=0.95.
   - konflikt (name=ZNAK, metric=DIALOG, np. styl „Sign” wyglądający jak dialog) → **DIALOG, conf=0.6** (metryka wygrywa, ale flaga niepewności).
   - oba UNKNOWN (np. `Q1`, pos≈0, punct średni) → conf=0.4 → kandydat do HITL.

**💪 Mocne:** Domyka wzajemne dziury (brief: nazwa~90% i metryka~90% z RÓŻNYMI dziurami → suma pokrycia istotnie wyższa, prawdopodobnie 96-98%). Daje **wbudowaną pewność** → naturalny trigger HITL (TP-3). Override `draw%` eliminuje najpewniejszy błąd. Całość offline/deterministyczna.
**⚠️ Słabe:** Więcej kodu niż P1/P2. Wymaga dostrojenia wag/progów na realnych plikach. Konflikty trzeba przemyśleć (reguła „metryka wygrywa” może czasem zawieść — stąd obniżona pewność, nie ślepy override).
**🎲 Ryzyko:** Przekombinowanie progów. Mityguje: zacznij prosto (reguły if/else, nie ML), iteruj na korpusie testowym. Niskie.
**⭐ Ocena: 9/10** — _Uzasadnienie:_ Najlepszy stosunek skuteczność/zgodność-z-zasadami. Bezpośrednio realizuje intencję usera („dużo da się heurystykami i badaniem złożoności ASS”). Daje confidence „za darmo” (klucz do TP-3). Nie 10, bo wymaga kalibracji i jest trochę kodu — ale to jedyny słaby punkt.
**🛡️ TP:** TP-1 ✅ (czysta heurystyka) · TP-2 ✅ · TP-3 ✅ (confidence → próg) · TP-4 ✅.

---

#### P4 — Scoring ważony ciągły (jeden wzór punktowy zamiast reguł)

**Opis:** Zamiast drzewa if/else — jeden wzór: `dialog_score = w1·punct% + w2·avg_len_norm − w3·pos% − w4·draw% + w5·name_bonus`. Próg na `dialog_score` decyduje, odległość od progu = pewność.

**Mechanizm:** Normalizuj metryki do [0,1], dobierz wagi ręcznie (np. `w_draw` bardzo duża ujemna). `score > 0.5 → DIALOG`. `|score−0.5|` mapuje na confidence.

**💪 Mocne:** Elegancki, jeden „pokrętło” (próg). Confidence wychodzi naturalnie z odległości. Łatwo dodać metrykę (nowy składnik).
**⚠️ Słabe:** Wagi trudniej intuicyjnie dostroić niż jawne reguły. Twardy sygnał `draw%` lepiej traktować jako override (P3) niż topić w sumie ważonej (duża waga ≠ gwarancja). Mniej czytelny przy debugowaniu („czemu to dialog?” → trzeba liczyć wzór).

#### P15 — ⭐ Naprawa `srt_to_ass`: mapowanie po czasie startu + zachowanie tagów

**Opis:** Zastąp kruche mapowanie po `srt_index` (które desynchronizuje się przy `continue`) **mapowaniem po czasie startu eventu** i zachowaj oryginalne tagi ASS, podmieniając tylko tekst widoczny.

**Mechanizm:** Problem (potwierdzony w kodzie, linie 399–411): pętla idzie po eventach ASS, używa licznika `srt_index`; gdy event ma tag `{...}` → `srt_index += 1; continue` (gubi przypisanie i przesuwa resztę). Naprawa:
1. Zbuduj indeks SRT po czasie: `{event.start → przetłumaczony_tekst}` (SRT i ASS dzielą tę samą oś czasu — pochodzą z tego samego pliku po `ass_to_srt`).

**💪 Mocne:** Rozwiązuje przyczynę („każdy ASS ma inną strukturę”) — czas startu jest stabilny niezależnie od struktury tagów. Zachowanie tagów = poprawny rendering znaków/efektów. Brak desynchronizacji (nie ma licznika, który się rozjeżdża). Deterministyczne, offline.
**⚠️ Słabe:** Wymaga, by `start` był spójny SRT↔ASS (jest, bo SRT powstaje z tego ASS w `ass_to_srt`). Eventy o identycznym `start` (rzadkie nakładki) → potrzeba tie-breakera (kolejność). Tagi środkowe (`\N` wewnątrz, inline `\i1`) → ostrożny split.
**🎲 Ryzyko:** Kolizje czasów. Mityguje: przy remisie `start` użyj kolejności wystąpienia jako wtórnego klucza. Niskie.
**⭐ Ocena: 9/10** — _Uzasadnienie:_ Celuje w prawdziwą przyczynę buga (krucha synchronizacja indeksów), nie w objaw. Mapowanie po czasie to standardowy, solidny wzorzec dla napisów. ### 3.2. Strategia decyzyjna #1 — 🧱 First Principles (od pierwszych zasad)

**Pytanie:** Co jest *fizycznie nieodzowne*, by zamienić folder MKV w polskiego lektora bez klikania?

Sprowadźmy do atomów:
1. **Musisz wiedzieć, którą ścieżkę audio i napisów wziąć.** → Informacja ta ISTNIEJE w pliku (metadane MKV). Nie trzeba jej *zgadywać* (LLM), trzeba ją *odczytać* (P8). **LLM tu byłby rozwiązywaniem problemu, który nie istnieje.**
2. **Musisz oddzielić mowę od nie-mowy w ASS.** → To jedyny atom z prawdziwą niepewnością. Ale „nie-mowa” ma fizyczne sygnatury: rysunki wektorowe (`\p`) to z definicji nie mowa; tekst spozycjonowany na ekranie (`\pos`) to prawie zawsze znak; zdania z interpunkcją to prawie zawsze mowa. **Te sygnatury są mierzalne bez rozumienia treści.** LLM „rozumie”, ale tu wystarczy „zmierzyć”.
3. **Musisz przełożyć i udźwiękowić.** → Już rozwiązane (translator + TTS).
4. **Musisz wiedzieć, kiedy NIE jesteś pewien.** → To wymaga miary pewności, nie inteligencji. Confidence z reguł (P3) wystarcza.

**Wniosek First Principles:** Z czterech atomów **trzy nie mają żadnej niepewności wymagającej AI** (to odczyt + przekształcenie), a czwarty (podział mowy) ma niepewność *mierzalną sygnaturami formatu*. **LLM nie jest pierwszą zasadą tego problemu — jest nadmiarowym narzędziem.** Pierwsze zasady prowadzą wprost do: **metadane (P8) + sygnatury ASS (P3) + miara pewności (P7).**

### 3.3. Strategia decyzyjna #2 — 💀 Premortem (wyobraź porażkę za 3 miesiące)

**Scenariusz:** Jest wrzesień 2026. Tryb auto został wdrożony i… zawiódł. Dlaczego?

| Hipotetyczna przyczyna zgonu | Prawdopodobieństwo | Mitygacja (którą wbudować OD RAZU) |
|---|---|---|
| **„Cichy lektor”** — styl `Sign`=dialog trafił do alt_subs, brak audio dla części kwestii; user zauważył dopiero przy oglądaniu | 🔴 Wysokie | P3 (metryka bije nazwę przy konflikcie) + **dry-run/raport pokazujący ile linii→dialog vs znak** przed egzekucją + log |
| **Zła ścieżka napisów** (signs zamiast pełnego dialogu) → lektor czyta tylko OP/ED | 🟡 Średnie | P10 (liczba linii) + sanity-check „dialog ma <N linii? to podejrzane → HITL” |
| **Auto utknął na `getch()`** bo translator=Gemini/ChatGPT (manualne) | 🔴 Wysokie | W trybie auto **wymuś** auto-backend (Google/DeepL API); jeśli wybrany manualny → ostrzeż/przełącz |
| **Jeden zły plik wykoleił cały batch 40 szt.** | 🟡 Średnie | P13: try/except per plik, raport błędów, kontynuuj resztę |
| **Za dużo pytań HITL** → user: „to nie jest auto!” | 🟡 Średnie | Kalibracja progów na dry-run; P11 (profile grup) tnie pytania dla codziennych źródeł |
| **`srt_to_ass` dalej psuje napisy poboczne** | 🟡 Średnie | P15 (mapowanie po czasie) + test na realnych ASS różnych grup |
| **Przekombinowane progi** → regresja vs ręczny | 🟢 Niskie | Zacznij od prostych reguł; tryb ręczny zawsze dostępny (TP-4) jako wyjście awaryjne |

**Wniosek Premortem:** Trzy najgroźniejsze tryby śmierci to (1) ciche gubienie dialogu, (2) zła ścieżka napisów, (3) zawieszenie na manualnym translatorze. **Żadnego z nich nie rozwiązuje LLM** — rozwiązują je: konfliktowa reguła metryka>nazwa, sanity-check liczby linii, wymuszenie auto-backendu, oraz **dry-run jako siatka bezpieczeństwa**. To przesuwa priorytet z „lepszy klasyfikator” na „lepsza widoczność + bezpieczne domyślne”.

### 3.4. Strategia decyzyjna #3 — 🎯 Pareto 80/20

**Pytanie:** Które 20% pracy daje 80% redukcji kliknięć?

Rozkład bólu (z FAZY 0): ekstrakcja ścieżek (~100 klik) + podział stylów (~120 klik) = **~73% wszystkich kliknięć**. Translacja/audio/liczby (per-plik Y/N) = ~27%.

| Praca | % redukcji bólu | Koszt wdrożenia | Pareto-ratio |
|---|:--:|:--:|:--:|
| **P8 auto-ścieżki** (zabija ~100 klik) | ~33% | Niski (parser + selekcja) | 🟢 **Najwyższy** |
| **P3+P7 auto-podział stylów** (zabija ~120 klik) | ~40% | Średni | 🟢 Wysoki |
| **P12 auto_mode** (zabija wszystkie per-plik Y/N tłum/audio/liczby) | ~27% | Niski | 🟢 Wysoki |
| P10/P11/P14 (jakość/turbo) | marginalne na kliknięcia | Średni | 🟡 Średni |
| P5/P6 LLM | ~0% na kliknięcia (to jakość detekcji, nie ilość) | Wysoki | 🔴 Najniższy |

**Wniosek Pareto:** ~95% redukcji kliknięć osiąga **trójka P8 + P3/P7 + P12** — wszystkie heurystyczne/architektoniczne, ZERO LLM. **LLM nie pojawia się w 20% dającym 80% efektu** — bo problem usera to *liczba decyzji*, nie *trudność pojedynczej decyzji*. To koronny argument: nawet gdyby LLM był darmowy i szybki, nie ruszyłby głównej bolączki bardziej niż heurystyka, bo ból = ilość interakcji, a nie jakość pojedynczej klasyfikacji.

### 3.5. Strategia decyzyjna #4 — 🔴 Red Team (atak na rekomendację „bez LLM”)

Załóżmy adwersarza forsującego LLM. Jego argumenty i kontra:

| 🔴 Atak Red Team | 🛡️ Obrona |
|---|---|
| „Heurystyka pęknie na nietypowym ASS, którego nie przewidziałeś. LLM generalizuje.” | Prawda częściowa — ale dla nieprzewidzianego przypadku mamy **confidence→HITL** (P7). Człowiek to lepszy fallback niż niedeterministyczny LLM, a przy tym zgodny z TP-1/TP-3. LLM lokalny (P5) jako *opcjonalny* drugi fallback zostaje dostępny — nie odrzucamy go, degradujemy do opcji. |
| „90% (sama metryka) to za mało dla produkcji.” | Dlatego rdzeń to nie sama metryka, lecz **hybryda P3 (~96-98%)** + profile grup P11 (dla codziennych źródeł ~99%) + HITL na resztę. 90% to dolna granica najsłabszego pojedynczego sygnału, nie systemu. |
| „User i tak ma Gemma + Gemini gotowe. Skoro są, czemu nie użyć?” | Bo „mam młotek” ≠ „to gwóźdź”. TP-1 mówi wprost: LLM = ostateczność. Dostępność narzędzia nie zmienia faktu, że metadane (P8) czynią je zbędnym dla A/B, a sygnatury (P3) dla C. Trzymamy P5 jako *włączalny* fallback — zjadane ciastko i mamy ciastko. |
| „Bez LLM utkniesz na dostrajaniu progów w nieskończoność.” | Dlatego **dry-run + log decyzji** (P13/P14) — kalibracja na realnych plikach usera w godziny, nie tygodnie. Progi to kilka liczb, nie model do trenowania (którego user nie chce — TP-1). |
| „LLM API (Gemini) jednym requestem sklasyfikuje wszystkie style — prościej niż reguły.” | Łamie **TP-2** (detekcja bez internetu) — twarda, nienegocjowalna zasada. Koniec dyskusji dla rdzenia. Może być świadomie-włączaną opcją „pomóż przy tym pliku”, nigdy domyślną. |

**Wniosek Red Team:** Najsilniejszy atak („heurystyka pęknie na nieznanym”) NIE obala rekomendacji — wzmacnia rolę **HITL + dry-run + opcjonalnego LLM lokalnego jako fallbacku**. Red Team nie znalazł scenariusza, w którym LLM *musi* być rdzeniem bez łamania TP-1/TP-2. Rekomendacja „heurystyka-first, LLM-opcjonalny” przetrwała atak.

### 3.6. Synteza FAZY 3

Cztery niezależne strategie (First Principles, Premortem, Pareto, Red Team) **zbiegają się do tej samej konkluzji**:

> **Rdzeń = heurystyka deterministyczna offline (P8 metadane + P3/P7 sygnatury+HITL + P12 flaga + P13 batch + P15 bugfix). LLM lokalny (P5) = wyłączalny fallback przy niskiej pewności. LLM API (P6) = odrzucony jako wymóg (łamie TP-2). Profile grup (P11) + cache (P14) = warstwa „turbo” na v2.**

Zbieżność czterech różnych soczewek to mocny sygnał, że to nie przypadek doboru kryteriów, lecz właściwość problemu.

### 🥇 FILAR 1 — Auto-selekcja ścieżek z metadanych (P8 + P9 + P10)

**Co to:** Warstwa, która z `mkvmerge -J` sama wybiera ścieżkę audio i właściwą ścieżkę napisów, bez pytania.

**Plan implementacji:**
1. **Rozszerz parser** (`mkvtoolnix.py::_parse_track_data`): dodaj do zwracanego dict: `track_name` (`properties.get('track_name','')`), `forced` (`forced_track`), `default` (`default_track`), `enabled`, oraz `num_lines` (`properties.get('num_index_entries')` lub `tag_number_of_frames`/parsing gdy brak). *(Empiryczna luka z FAZY 0.2 — dziś czytane są tylko `language`/`language_ietf`.)*
2. **Nowy moduł selekcji** `auto_select.py` (lub metody w `MkvToolNix`): `select_audio_track(tracks, prefs) → track_id`, `select_subtitle_track(tracks, prefs) → track_id`.
   - Audio: filtruj `type=='audio'`; sortuj wg `prefs.audio_lang_priority`; remis → `default` then najniższe `id`.
   - Napisy: filtruj `type=='subtitles'`; wg `prefs.subs_lang_priority` (pol>eng>pierwsza); jeśli >1 kandydat w tym samym języku → **P10**: wybierz po `num_lines` (max) i odrzuć te z `track_name ~ /sign|song/i`.
3. **Refaktor `mkv_extract_track`:** rozdziel selekcję (które ID) od egzekucji (mkvextract). Ręczny tryb → pętla `input()` (jak dziś). Auto → wynik `select_*`.
4. **Sanity-check:** jeśli wybrana ścieżka napisów ma podejrzanie mało linii (np. <50 dla pełnego odcinka) → oznacz `low_confidence` → HITL.

**Zależności:** `mkvmerge` (już jest). Brak nowych bibliotek. Pola JSON do zweryfikowania na realnych plikach (czy `num_lines` jest w `-J`, czy trzeba lekkiego parsu).

**Ryzyka + mitygacja:**
- `language: und` / brak tagów → fallback na `track_name`, potem HITL. *(Mit.: nie zakładaj, że language zawsze jest.)*
- `num_lines` nieobecne w JSON dla niektórych kodeków napisów → policz linie szybkim parsem ASS/SRT (tani, bo tekst). *(Mit.: lazy-parse tylko gdy potrzebne.)*
- Dwie ścieżki audio JP (np. komentarz + główna) → preferuj `default`, potem dłuższą.

**Metryki sukcesu:**
- ≥95% odcinków: ścieżka audio i napisów wybrana auto bez HITL.
- 0 przypadków wyboru ścieżki „signs” jako głównego dialogu na korpusie testowym Erai-raws.
- Czas selekcji <100 ms/plik (czysty odczyt JSON).

**Dlaczego pierwszy:** Najwyższy Pareto-ratio (zabija ~100 klik), najniższe ryzyko, wzorcowa zgodność z TP-1/TP-2, fundament pod resztę. „Najtańsze złoto”.

### 🥈 FILAR 2 — Auto-podział stylów: hybryda + HITL (P3 + P1 + P2 + P7) [+ P5 opcjonalny]

**Co to:** Serce trudnego pod-problemu C. Zastępuje ręczny `_select_styles` scoringiem z wbudowaną pewnością i bramą człowieka przy niepewności.

**Plan implementacji:**
1. **Ekstraktor metryk** `style_metrics.py`: `compute_style_metrics(subs) → {style: {pos_pct, draw_pct, punct_pct, avg_len, line_count, share}}`. Jeden przebieg po `subs.events`; regexy z brief'u:
   - pos: `r'\\(pos|move|clip|fad|t)\b'` (lub `\(`)
   - draw: `r'\\p[1-9]'`
   - punct: tekst po zdjęciu tagów kończy się na `[.?!…]`
2. **Klasyfikator** `classify_styles(metrics, names) → {style: (label, confidence)}` wg reguł fuzji P3 (sekcja P3.mechanizm). Twardy override `draw_pct>30 → ZNAK conf .99`.
3. **Integracja w `split_ass`:** jeśli `auto_mode` → użyj `classify_styles`; style z `label==DIALOG ∧ conf≥próg` → `selected_styles` (main/TTS); reszta → alt. Style z `conf<próg` → kolejka HITL.
4. **HITL zbiorczy** (P7): zbierz niepewne ze WSZYSTKICH plików, pokaż jeden ekran z sugestią i metrykami; domyślna akcja = sugestia (Enter akceptuje). *(Nie przerywaj per-plik.)*
5. **(Opcjonalnie, v2) Fallback P5:** jeśli `auto_llm_fallback==true ∧ conf<próg` → zapytaj lokalną Gemmę (próbka linii stylu) zamiast/przed HITL. Domyślnie OFF (TP-1).

**Zależności:** `pysubs2` (już jest — `split_ass` go używa). Regex. Opcjonalnie llama.cpp/moduł GGUF z EchoReadera (tylko dla v2 fallback).

**Ryzyka + mitygacja:**
- **Cichy lektor** (dialog→alt): override metryka>nazwa przy konflikcie + dry-run pokazujący podział + log. *(Najgroźniejszy tryb z Premortem.)*
- Krótki dialog bez interpunkcji (`punct%` niski) → nie klasyfikuj jako znak tylko z tego powodu; wymagaj też `pos%` wysokiego lub `draw%`. Reguła: ZNAK wymaga *pozytywnego* sygnału (pos/draw), nie tylko *braku* interpunkcji.
- Karaoke `\k` bez `\pos` → traktuj `\k`/`\kf` jako sygnał ZNAK (to OP/ED).
- Progi nietrafione → kalibracja na dry-run + log; start od konserwatywnych (raczej pytaj niż zgadnij źle).

**Metryki sukcesu:**
- ≥96% stylów sklasyfikowanych auto (zgodność z decyzją usera) na korpusie testowym; cel z profilami grup ≥99%.
- 0 przypadków „cichego lektora” (dialog wrzucony do alt bez HITL) na korpusie.
- <5% odcinków trafia do HITL.
- Każda decyzja zalogowana z metrykami (audytowalność).

**Dlaczego drugi:** To jedyny pod-problem z realną niepewnością i największy pojedynczy blok kliknięć (~120). Trudniejszy niż Filar 1, ale to tu „bije serce” trybu auto. HITL czyni go bezpiecznym.

### 🥉 FILAR 3 — Orkiestracja wsadowa + flaga + bugfix (P12 + P13 + P15) [+ P11/P14 v2]

**Co to:** Spina filary 1-2 w „folder → output”, dodaje flagę trybu, dry-run, raport, izolację błędów i naprawia obieg napisów pobocznych.

**Plan implementacji:**
1. **Flaga** (`settings.py`): dodaj `auto_mode: bool = False` (+ `auto_audio_lang_priority`, `auto_subs_lang_priority`, `auto_dialog_conf_threshold`, `auto_llm_fallback: bool=False`) do dataclass, `load_from_file` (`data.get(..., default)`), `change_settings_save_to_file`. Wsteczna kompatybilność: brak pola → `False`.
2. **Branch w `main()`:** `if settings.auto_mode: run_auto_pipeline(settings) else: <obecny flow nietknięty>`.
3. **`run_auto_pipeline`** (P13): 
   - Faza DETEKCJI (bez ciężkiego I/O): dla każdego MKV zbuduj `plan` (audio_id, subs_id, dialog_styles, confidences). 
   - Faza HITL: jeśli niepewności — jeden zbiorczy ekran. 
   - Faza DRY-RUN (jeśli `--dry-run` lub pole): wypisz plan + zakończ. 
   - Faza EGZEKUCJI: per plik w `try/except` — extract → refactor → translate(auto-backend) → audio → process. Błąd jednego ⇒ log + kontynuuj. 
   - Faza RAPORT: tabela sukces/HITL/błąd per plik.
   - **Wymuszenie auto-backendu translacji** (z Premortem): jeśli `settings.translator` ∈ {Gemini, ChatGPT} → w auto przełącz na Google/DeepL API lub ostrzeż i przerwij (nie zawieszaj na `getch()`).
4. **Bugfix `srt_to_ass`** (P15): przepisz mapowanie z `srt_index` na klucz `event.start` (±tolerancja), zachowaj tagi przez `re.split(r'({[^}]*})', text)`, brak dopasowania → zostaw oryginał. Test na ASS z 3+ różnych grup.
5. **(v2) Profile grup (P11) + cache (P14):** parsuj `[Grupa]` z nazwy; profil jako prior; zapisuj decyzje do `auto_decisions.json`; po HITL aktualizuj profil.

**Zależności:** Filary 1-2 (selekcja + klasyfikacja). `pysubs2` (bugfix). Reszta to logika sterowania.

**Ryzyka + mitygacja:**
- Duplikacja logiki auto/ręczny → współdziel rdzeń (selekcja vs egzekucja rozdzielone w Filarze 1). *(Mit.: jedna funkcja egzekucji, dwa źródła decyzji.)*
- Przerwanie w połowie batcha → v1: raport co zrobione; v2: wznawianie z cache (P14).
- Złożoność orkiestratora → MVP = happy path + try/except per plik; bez wznawiania.
- Bugfix wprowadzi regresję → testy na realnych ASS + zachowanie fallbacku „zostaw oryginał”.

**Metryki sukcesu:**
- Folder 40 MKV → ≤2 interakcje łącznie (1× start, ewentualnie 1× zbiorczy HITL).
- 1 zły plik nie zatrzymuje pozostałych 39 (test: wstaw uszkodzony MKV).
- `srt_to_ass`: 100% napisów pobocznych poprawnie scalonych na korpusie (vs dziś — desync).
- Tryb ręczny: bit-identyczne zachowanie jak przed zmianą (regresja = 0).

**Dlaczego trzeci:** Bez Filarów 1-2 nie ma czego orkiestrować — ale to ten filar *dostarcza obietnicę* „wrzucam folder, wychodzi output”. Największy kawałek nowego kodu, więc po fundamentach.

## 🗂️ FAZA 5 — Podział kontekstowy (w TYM projekcie)

Co w tym konkretnym repo gra na korzyść, co przeszkadza, a co jest zależne od decyzji/weryfikacji.

### ✅ DOBRE (atuty tego projektu — wykorzystaj)

- **Pipeline obliczeniowo gotowy.** Extract/translate/TTS/merge działają. Tryb auto to warstwa decyzji NAD sprawnym rdzeniem, nie przepisywanie. Mały delta-kod.
- **Metadane już częściowo czytane.** `_parse_track_data` zwraca `language`/`language_ietf` → dołożenie `track_name`/`num_lines` to mała zmiana, nie nowy podsystem.
- **Podział main/alt już istnieje.** `split_ass` rozdziela dialog↔znaki sprawnie (pysubs2). Wymienić trzeba TYLKO źródło decyzji (`input()` → scoring), nie mechanikę.
- **Wyjście jednokierunkowe (→PL) potwierdzone w kodzie.** `mkv_merge` hardkoduje `pol`/`Lektor PL` → problem detekcji zawężony do „co jest dialogiem/znakiem”, kierunek stały.
- **Settings ma czysty wzorzec rozszerzania** (`dataclass` + `data.get` z defaultami) → flaga `auto_mode` wpina się bez bólu, wstecznie kompatybilnie (TP-4 za darmo).
- **User już używa auto-backendu** (`Google Translate` w settings.json) → tryb auto realny bez zmiany jego nawyków translacyjnych.
- **Codzienne, powtarzalne źródła** (te same grupy wydawnicze) → profile grup (P11) dadzą wysoki zwrot; „samouczenie bez ML” idealnie pasuje do TP-1.
- **Zasoby LLM dostępne, ale niewymagane** (Gemma GGUF w EchoReader, geminicli2api) → fallback P5 jest *realny* gdyby był potrzebny, bez wpychania go w rdzeń.

### ⚠️ ZŁE / RYZYKOWNE (przeszkody — zaadresuj)

- **`slots=True` w `Settings`** → nie da się przypisać pola spoza definicji; każde nowe pole MUSI być w dataclass + we wszystkich miejscach konstrukcji (`load_from_file`, `get_user_settings`, `change_settings_save_to_file`). Łatwe przeoczenie → `TypeError`.
- **`mkv_extract_track` splata selekcję z egzekucją** (jedna pętla `input()`+`mkvextract`). Trzeba rozdzielić, by auto i ręczny dzieliły egzekucję. Refaktor, nie dopisanie.
- **`srt_to_ass` jest realnie zbugowany** (potwierdzone, linie 399–411: desync `srt_index` przy `continue`). Bez P15 obieg napisów pobocznych w trybie auto będzie cicho psuł pliki.
- **Translatory manualne na ścieżce krytycznej.** `translate_gemini`/`translate_chat_gpt` używają `getch()`/kopiuj-wklej → w trybie auto ZAWIESZĄ batch. Trzeba twardego wymuszenia auto-backendu.
- **Mapowanie translatora po stringu** (`'Gemini Pro' in settings.translator`, `translate_srt` dict po nazwie) — kruche; uwaga: `settings.json` ma `"Google Translate"` ale `Config.get_translators()` zwraca `'Google Translate'` (OK), jednak literałowe nazwy są wrażliwe na literówki. Auto-tryb musi walidować nazwę backendu.
- **`num_lines` może nie być w `-J`** dla każdego kodeka napisów → potrzebny lazy-parse jako fallback (drobny narzut).
- **Brak testów integracyjnych pipeline'u** (katalog `tests/` to głównie eksperymenty TTS/translator). Dry-run + log decyzji muszą pełnić rolę „testów na żywych danych”.

### 🔗 ZALEŻNE (do weryfikacji / decyzji usera przed implementacją)

- **Czy `mkvmerge -J` zwraca `num_index_entries`/liczbę linii** dla ASS/SRT na realnych plikach usera? → determinuje, czy P10 potrzebuje lazy-parse. *(Weryfikacja: 1 komenda na próbce.)*
- **Jakie konkretnie grupy wydawnicze** user przetwarza najczęściej? → determinuje, czy P11 (profile) opłaca się od razu czy w v2. *(Pytanie do usera.)*
- **Próg pewności HITL** — ile pytań user toleruje? „Zero, chyba że naprawdę trzeba” vs „wolę potwierdzić”. → kalibracja progu. *(Pytanie + dry-run.)*
- **Czy chce dry-run domyślnie** (pokaż plan, potem wykonaj) czy „od razu rób”? → UX orkiestratora.
- **Czy fallback LLM lokalny w ogóle wdrażać w v1**, czy zostawić HITL jako jedyny fallback do v2? → zakres MVP. *(Rekomendacja: HITL w v1, LLM w v2.)*
- **Tolerancja czasowa dopasowania w P15** (±ile ms) → zależna od tego, czy `ass_to_srt` zachowuje czasy 1:1 (prawdopodobnie tak).

## ✅ FAZA 6 — REKOMENDACJA FINALNA

### 6.1. Odpowiedź na główne pytanie usera

> **„Czy musimy stosować LLM do auto-rozpoznawania, czy da się to inaczej zautomatyzować? CO POLECASZ?”**

**NIE — LLM nie jest potrzebny jako rdzeń, i nie polecam go jako rdzenia. Polecam czystą heurystykę offline, z LLM lokalnym tylko jako wyłączalny fallback i HITL jako główną siatkę bezpieczeństwa.**

To nie jest kompromis ani ostrożność — to wynika z **natury problemu**, potwierdzony przez cztery niezależne soczewki analityczne (First Principles, Premortem, Pareto, Red Team), które wszystkie zbiegły się do tej samej konkluzji.

### 6.2. Dlaczego heurystyka, a nie LLM — trzy twarde argumenty

1. **Informacja już istnieje — nie trzeba jej zgadywać (A/B).** Język i rola ścieżek to **metadane MKV** (`language`, `track_name`, liczba linii). To odczyt, nie inferencja. LLM rozwiązywałby tu nieistniejący problem. *(First Principles + brief empiryczny.)*

2. **Jedyna realna niepewność (podział stylów, C) jest mierzalna sygnaturami formatu, nie semantyką.** Rysunek wektorowy (`\p`) to z definicji nie mowa; tekst spozycjonowany (`\pos`) to prawie zawsze znak; zdanie z interpunkcją to prawie zawsze mowa. **Hybryda nazwa+metryka (P3) domyka wzajemne dziury sygnałów** (brief: każdy ~90% osobno, z RÓŻNYMI dziurami → ~96-98% razem), a profile grup (P11) podbijają to do ~99% dla codziennych źródeł. LLM „rozumie treść”, ale tu wystarcza „zmierzyć formę”.

3. **Ból usera to ILOŚĆ decyzji (~300 kliknięć), nie TRUDNOŚĆ pojedynczej.** Pareto: ~95% redukcji kliknięć daje trójka P8+P3/P7+P12 — sama architektura i heurystyka. **LLM nie pojawia się w 20% dającym 80% efektu.** Nawet darmowy i natychmiastowy LLM nie ruszyłby głównej bolączki bardziej niż heurystyka.

Dodatkowo: LLM jako rdzeń **łamie Tablicę Prawdy** — API łamie TP-2 (detekcja bez internetu) wprost; lokalny jako *wymóg* łamie TP-1 (niezależność od LLM) i jest wolny/niedeterministyczny. Heurystyka jest deterministyczna, offline, audytowalna i szybka (<100 ms/plik dla selekcji).

### 6.3. Rekomendowana architektura (rdzeń + warstwy)

```
╔═══════════════════════════════════════════════════════════════════╗
║  RDZEŃ (deterministyczny, offline, BEZ LLM) — MVP                   ║
║                                                                     ║
║  A/B ŚCIEŻKI:  P8 metadane (language + track_name)                  ║
║                + P10 dialog-vs-signs po liczbie linii               ║
║                + P9 konfigurowalne preferencje                      ║
║                                                                     ║
║  C STYLE:      P3 hybryda nazwa+metryka (scoring + confidence)      ║
║                = P1 metryki ∪ P2 nazwy, override draw% → ZNAK        ║
║                                                                     ║
║  NIEPEWNOŚĆ:   P7 confidence < próg → zbiorczy HITL (TP-3)          ║
║                                                                     ║
║  ARCH:         P12 flaga auto_mode (TP-4) + P13 batch + dry-run     ║
║                + wymuszenie auto-backendu translacji                ║
║                                                                     ║
║  BUGFIX:       P15 srt_to_ass — mapowanie po czasie startu          ║
╠═══════════════════════════════════════════════════════════════════╣
║  WARSTWA „TURBO” (v2, po działającym MVP)                           ║
║  P11 profile per-grupa  +  P14 cache/pamięć decyzji                 ║
╠═══════════════════════════════════════════════════════════════════╣
║  FALLBACK (opcjonalny, domyślnie OFF, NIGDY na ścieżce krytycznej)  ║
║  P5 LLM lokalny (Gemma GGUF) przy conf<próg — alternatywa dla HITL  ║
║  P6 LLM API — odrzucony jako wymóg (łamie TP-2); tylko jawnie on    ║
╚═══════════════════════════════════════════════════════════════════╝
```

### 6.4. Rola LLM — precyzyjnie

- **LLM lokalny (Gemma GGUF) — TAK, ale tylko jako opcja v2.** Wpięty za progiem pewności: `if auto_llm_fallback ∧ confidence < próg → zapytaj Gemmę zamiast/przed HITL`. Domyślnie **wyłączony**. Spełnia TP-2 (offline). To honoruje „mam to narzędzie” bez łamania „LLM = ostateczność”. Jego przewaga nad HITL: nie wymaga obecności człowieka. Jego wada: wolniejszy, niedeterministyczny — dlatego tylko dla <5% niepewnych przypadków.
- **LLM API (Gemini/ChatGPT) — NIE jako element trybu auto detekcji.** Łamie TP-2. Może istnieć wyłącznie jako świadomie-włączana, jednorazowa „pomoc przy trudnym pliku”, gdy user sam akceptuje sieć. Nigdy domyślnie, nigdy w batchu.
- **HITL > LLM jako domyślny fallback.** Człowiek przy realnej niepewności jest bezpieczniejszy, deterministyczny i zgodny z TP-1/TP-3. LLM lokalny to *wygodniejszy* (bezobsługowy) fallback dla usera, który nie chce nawet zbiorczego HITL — stąd opcja, nie domyślność.

### 6.5. Jednozdaniowa rekomendacja

> **Zbuduj tryb auto na deterministycznej heurystyce offline — metadane MKV dla ścieżek (P8/P10) i hybrydowy scoring nazwa+metryka dla stylów (P3) z progiem pewności kierującym do zbiorczego HITL (P7) — opakowane flagą `auto_mode` (P12) i orkiestratorem wsadowym z dry-run (P13), z naprawionym `srt_to_ass` (P15); LLM lokalny zostaw jako wyłączalny fallback na v2, a LLM API pomiń w detekcji. To rozwiązuje ~95% kliknięć bez łamania żadnej z czterech świętych zasad.**

## 🔚 Zamknięcie

**Konkluzja całości:** Problem usera jest po stronie *ilości interakcji*, nie *trudności decyzji*. Trzy z czterech pod-decyzji to odczyt metadanych (zero AI), czwarta jest mierzalna sygnaturami formatu ASS (heurystyka > LLM dla tego konkretnego zadania). LLM byłby rozwiązaniem szukającym problemu — a Tablica Prawdy (zwłaszcza TP-1 i TP-2) i tak by go zdegradowała do opcji. Rekomendacja „heurystyka-first, HITL jako siatka, LLM lokalny jako wyłączalny fallback v2” przetrwała atak Red Team i jest zbieżnym wnioskiem czterech niezależnych strategii decyzyjnych.
